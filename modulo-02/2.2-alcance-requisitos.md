## Clase 2.2.1 — Descripción General

**Tipo:** 📄 Lectura — Soluciones de Seguridad Protego

### 💡 Ideas clave

- Gran parte del trabajo de Protego consiste en auditorías de seguridad y pentests para certificar que las organizaciones cumplen con regulaciones.
- El evaluador debe estar familiarizado con los marcos de cumplimiento relevantes para cada cliente.
- Repaso del Módulo 1: permiso escrito para atacar + metodologías (PTES, OSSTMM, ISSAF, NIST, OWASP).
- En esta sección: **reglas de compromiso, lista de objetivos dentro del alcance, y validación del alcance**.

## Clase 2.2.2 — Reglas de Compromiso

**Tipo:** 📄 Lectura

### 📋 Elementos de un documento de Reglas de Compromiso (RoE)

| Elemento | Ejemplo |
|----------|---------|
| **Prueba de línea de tiempo** | Tres semanas, especificadas en diagrama de Gantt |
| **Ubicación de la prueba** | Sede de la empresa en Raleigh, Carolina del Norte |
| **Ventana de tiempo de la prueba** | De 8:00 a.m. a 5:00 p.m. hora del este de EE.UU. |
| **Método de comunicación preferido** | Informe final y reuniones semanales de actualización |
| **Controles de seguridad que podrían detectar/evitar las pruebas** | IPS, cortafuegos, DLP |
| **IPs o redes desde las que se originarán las pruebas** | 10.10.1.0/24, 192.168.66.66, 10.20.15.123 |
| **Tipos de pruebas permitidas o no permitidas** | Solo apps web; sin ingeniería social; SQL solo en ambientes dev/stage |

### 📊 Diagrama de Gantt — Ejemplo (SecretCorp)

```
SecretCorp Penetration Testing Project Plan
─────────────────────────────────────────────────────────────
Day 1    9   17   25   33   41   49   57   65   73   81   89
  │
  ├── Pre-engagement tasks ──── 6 days
  │
  ├── Penetration Testing of App 1 ──────────────── 15 days
  │                                    (días 41-65)
  ├── Penetration Testing of App 2 ──────────────── 15 days
  │                                              (días 65-89)
  ├── Report Delivery ────────────────────────────── 1 day
  └── Knowledge Transfer ──────────────────────────── 3 days
```

> 💡 Las herramientas para documentar la línea de tiempo incluyen: **Diagramas de Gantt** y **Estructuras de Desglose del Trabajo (WBS)**.

> 📌 El **permiso de prueba (o permiso de ataque)** es otro documento clave — puede ser independiente o estar incluido en el contrato principal.

## Clase 2.2.3 — Práctica: Reglas de Compromiso ✅

**Tipo:** Verificación de conocimientos

**¿Cuáles son los tres componentes relevantes para las reglas de compromiso?**

> ✅ **Respuesta correcta:**
> - ✔️ La línea de tiempo de las pruebas
> - ✔️ Las horas del día en que se realizarán las pruebas
> - ✔️ Los tipos de pruebas que se permitirán o no

> ❌ No forman parte de las RoE: acceso al código fuente · nombres y credenciales del personal · costo y calendario de pagos

## Clase 2.2.4 — Lista de Objetivos y Activos Dentro del Alcance

**Tipo:** 📄 Lectura

### 🎯 El alcance debe incluir

- Todos los **sistemas, aplicaciones y redes** que se probarán
- **Rangos de direcciones IP** de los dispositivos y activos
- **Redes inalámbricas / SSIDs** que se pueden o no probar
- **Documentación de API** disponible

### 📡 Tipos de documentación de API

| Tipo | Descripción | URL |
|------|-------------|-----|
| **SOAP** | Basado en XML y esquemas XSD | w3.org/TR/soap |
| **Swagger (OpenAPI)** | Marco de documentación de APIs REST — el tipo más común hoy | swagger.io |
| **WSDL** | Lenguaje basado en XML para documentar servicios web | w3.org/TR/wsdl20-primer |
| **GraphQL** | Lenguaje de consulta para APIs + runtime del lado del servidor | graphql.org/learn |
| **WADL** | Lenguaje basado en XML para describir aplicaciones web | w3.org/Submission/wadl |

### 📦 Recursos de soporte que el cliente puede proveer

| Recurso | Descripción |
|---------|-------------|
| **SDK** | Herramientas de desarrollo para entender plataformas y apps especializadas del cliente |
| **Código fuente** | Algunas organizaciones permiten acceso al código de las apps a probar |
| **Ejemplos de requests** | Se pueden obtener también con proxies como Burp Suite o OWASP ZAP |
| **Diagramas de red/arquitectura** | Muy beneficiosos para definir qué está dentro del alcance |

### ⚠️ Causas comunes de aumento de alcance (scope creep)

| Causa | Descripción |
|-------|-------------|
| **Mala gestión de cambios** | No se controlan los cambios durante la interacción |
| **Elementos no identificados** | Falta de identificación de elementos técnicos y no técnicos necesarios |
| **Mala comunicación** | Poca comunicación entre partes interesadas y el equipo |

> 💡 Si el cliente solicita trabajo adicional fuera del SOW original → solicitar que se firme y acuerde **una nueva SOW**.

## Clase 2.2.5 — Práctica: Lista de Objetivos y Activos Dentro del Alcance ✅

**¿Qué recursos técnicos pueden identificarse según el alcance?**

> ✅ **Respuesta correcta:**
> - ✔️ Documentos de topología de red y arquitectura del sistema
> - ✔️ SSID inalámbricos
> - ✔️ Documentación de API

> ❌ No son recursos técnicos del alcance: NDAs · credenciales del equipo · SLA

## Clase 2.2.6 — Validación del Alcance del Compromiso

**Tipo:** 📄 Lectura

### 👤 Preguntas para entender la audiencia objetivo del informe

| Pregunta | Propósito |
|----------|-----------|
| ¿Cuál es la necesidad de la entidad o individuo? | Determinar el destinatario principal del informe |
| ¿Cuál es la posición del destinatario principal? | Adaptar nivel técnico del informe |
| ¿Cuál es el propósito del compromiso? | Objetivo y finalidad del pentest |
| ¿Cuál es la responsabilidad y autoridad del destinatario? | ¿Puede tomar decisiones basadas en los hallazgos? |
| ¿A quién se dirige el informe? | ISM, CISO, CIO, CTO, equipos técnicos... |
| ¿Quién más tendrá acceso al informe? | Control de acceso a información confidencial |

### 📞 Documentación de comunicación con stakeholders

| Elemento | Descripción |
|----------|-------------|
| **Info de contacto** | Datos de todas las partes interesadas |
| **Proceso de comunicación** | Canal y formato de comunicación |
| **Frecuencia** | ¿Cada cuánto interactuar con los stakeholders? |
| **Contactos de emergencia** | Personas disponibles en cualquier momento ante una emergencia |

**Figura 2-2 — Tarjeta de contacto (campos requeridos):**
```
┌─────────────── PRIMARY STAKEHOLDER ───────────────┐
│ Name                    Email                      │
│ Title                   Responsibility             │
│ Work Number  Mobile     Other Number  Alt. Email   │
│ Address                 Notes                      │
│ City                    State    ZIP Code          │
├─────────────── EMERGENCY CONTACTS ────────────────┤
│ Primary Contact         Secondary Contact          │
│ Phone    Email          Phone    Email             │
│ Address                 Address                    │
│ City, ST ZIP            City, ST ZIP               │
└───────────────────────────────────────────────────┘
```

### 🔐 Transferencia segura de datos
- Usar **SCP** o **SFTP** para transferencia/almacenamiento masivo
- Intercambiar **claves PGP** o **S/MIME** para correo electrónico cifrado

### 💰 Preguntas de presupuesto y ROI

**Del lado del cliente:**
- ¿Cómo justifico el costo de las pruebas de penetración a mi jefe?
- ¿Por qué necesitamos pruebas si ya tenemos controles técnicos?
- ¿Cómo calculo el ROI?
- ¿Puedo hacerlo yo mismo?

**Del lado del evaluador:**
- ¿Cómo evito exceder el presupuesto?
- ¿Cómo precio el servicio?
- ¿Cómo demuestro el ROI al cliente?

### 📊 Figura 2-3 — Evaluación de un momento dado

Las pruebas de penetración son evaluaciones en un **momento específico**, no una garantía permanente de seguridad.

| | Pen Test 1 (Ahora) | Pen Test 2 (1 año) | Pen Test 3 (2 años) |
|-|---|---|---|
| **Sistemas evaluados** | 1,000 | 1,100 | 2,200 |
| **Críticas** | 5 | 3 | 15 |
| **Altas** | 11 | 31 | 22 |
| **Medias** | 32 | 10 | 8 |
| **Bajas** | 45 | 7 | 15 |

> ⚠️ Las pruebas de penetración por sí solas no garantizan la seguridad total. El evaluador también debe incorporar **estrategias de mitigación claras y viables** + análisis de impacto + plazos de corrección con las partes interesadas.

## Clase 2.2.7 — Estrategia: Pruebas en Entornos Desconocidos y Conocidos

**Tipo:** 📄 Lectura

| Tipo | Antes conocido como | Info recibida | Perspectiva |
|------|--------------------|----|-------------|
| **Entorno desconocido** | Caja negra | Solo dominios e IPs | Atacante externo sin conocimiento previo; staff puede no saber cuándo se hará la prueba |
| **Entorno conocido** | Caja blanca | Diagramas, IPs, configs, credenciales, código fuente | Identificar el mayor número de vulnerabilidades posible; alcance amplio |

> 💡 Con la sofisticación actual de los adversarios, el enfoque de **entorno desconocido suele ser una buena opción** ya que simula mejor a un atacante real.

---

## Clase 2.2.8 — Práctica: Estrategia Entorno Desconocido/Conocido ✅

**En una prueba en entorno desconocido, ¿qué información se proporciona al equipo?**

> ✅ **Respuesta correcta:** Información mínima — puede incluir direcciones IP y nombres de dominio.

> ❌ No se proporciona: infraestructura y configuraciones · código fuente · diagramas de topología

**Data Center — Servidores:**

---

### 📋 Hoja de Trabajo del Alcance — Nexus Plaza

| Pregunta | Respuesta |
|----------|-----------|
| **1. Mayores preocupaciones de seguridad** | Ataque de ransomware al sistema de inventario y envío que impida cumplir pedidos a tiempo |
| **2. Qué probar** | Clústeres Operaciones (172.26.0.0/21) y Logística (172.27.0.0/21); SQL Server en entorno de desarrollo |
| **3. Qué NO probar** | Clústeres Admin y Amazon Support; infraestructura de la tienda Amazon |
| **4. ¿Producción o pruebas?** | Producción (con restricciones); SQL Server solo en entorno de desarrollo (réplica) |
| **5. Acceso interno** | Sí — VLAN aislada del departamento de TI |
| **6. Sistemas de usuario final** | No incluidos en el alcance |
| **¿Ingeniería social?** | Sí, limitada a lista específica de correos del personal de almacén |
| **¿Ataques disruptivos/DoS?** | Sí, solo en ventana de mantenimiento: 2:00–6:00 a.m. (viernes, sábado, domingo) |
| **Dispositivos de seguridad** | Firewalls con IDS integrado (entre DC y LAN) + firewalls locales en cada servidor |
| **7. ¿Acceso inalámbrico?** | No — fuera del alcance |
| **8. ¿Servicios web?** | No — Amazon alojado externamente, fuera del alcance |
| **9. ¿Empleados informados?** | Solo personal TI directamente responsable de monitorear operaciones/logística |
| **10. Ubicación del DC** | Houston, Texas |

---

### 📋 Reglas de Compromiso — Nexus Plaza

| Elemento | Valor |
|----------|-------|
| **Línea de tiempo** | Inicio: 2 semanas post-firma; Informe final: 60 días |
| **Ubicación** | Centro de datos en Houston; acceso interno vía VLAN del departamento de TI |
| **Ventanas de prueba** | No disruptivas: horario laboral normal; Disruptivas: 2:00–6:00 a.m. (viernes a domingo) |
| **Comunicación** | Informe final + teleconferencias y reportes de actualización semanales |
| **Controles de seguridad** | Firewalls, IDS, firewalls locales en servidores, VPN (SSL/IPsec) |
| **Manejo de datos sensibles** | Bajo NDA; uso de entorno de desarrollo para pruebas críticas |
| **IPs de origen de pruebas** | Desde VLAN interna del departamento de TI |
| **Pruebas permitidas** | Escalamiento de privilegios, pruebas internas, evaluación de vulnerabilidades, ingeniería social limitada |
| **Pruebas NO permitidas** | Ataques a infraestructura Amazon; interrupciones fuera de horario; ataques que afecten producción directamente |
| **Contactos del cliente** | Director de TI · Gerente de almacén · Gerente de operaciones |

### ✅ Verificación de habilidades
**¿Cuál es la mayor preocupación del cliente con respecto al alcance?**
> ✅ Que los sistemas de **inventario y envío** pueden ser vulnerables al **ransomware** → podría impedir cumplir pedidos.

## Clase 2.2.10 — Lab: Creación de un Acuerdo de Prueba de Penetración

**Tipo:** 🧪 Laboratorio — Redacción de contrato (cliente ficticio: Nexus Plaza)

### 📄 Acuerdo de Prueba de Penetración — Protego / Nexus Plaza

#### a. Partes del acuerdo
| Parte | Detalles |
|-------|---------|
| **Cliente** | Nexus Plaza — Houston, TX (rep: Director de TI / CEO) |
| **Proveedor** | Protego Security Solutions — San Francisco, CA (rep: Alex Prevost; supervisor: Matt Willis) |

#### b. Alcance del trabajo

**El evaluador (Protego) acepta:**
- Realizar pruebas de penetración autorizadas en infraestructura interna de Nexus Plaza
- Evaluar seguridad de redes internas, sistemas de inventario, logística y entorno de desarrollo SQL Server
- Simular ataques controlados (escalamiento de privilegios, ingeniería social limitada)
- Respetar el alcance — evitar sistemas Amazon y producción directa
- No alterar datos de producción ni afectar servicios críticos
- Ejecutar pruebas de alto impacto solo en ventanas de mantenimiento autorizadas
- Documentar y reportar vulnerabilidades de forma responsable

**El cliente (Nexus Plaza) acepta:**
- Proporcionar acceso controlado vía VLAN aislada del departamento de TI
- Entregar documentación de red y arquitectura
- Proveer acceso al entorno de desarrollo SQL Server (réplica de producción)
- Informar al personal técnico clave sobre las pruebas
- Asegurar soporte técnico durante el compromiso
- Autorizar explícitamente las actividades dentro del alcance definido

#### c. Plazo
| Hito | Fecha |
|------|-------|
| Inicio del proyecto | 2 semanas post-firma del contrato y NDA |
| Duración total | 60 días calendario |
| Pruebas disruptivas | Vie-Sáb-Dom, 02:00–06:00 a.m. (hora local) |
| Pruebas no disruptivas | Horario laboral normal |
| Informe final | Dentro de los 60 días |
| Actualizaciones de progreso | Reuniones semanales |

#### d. Tarifas y pagos
- Costo definido antes del inicio entre PSS y Nexus Plaza
- **50%** al inicio del compromiso
- **50%** al entregar el informe final
- Herramientas y licencias de PSS incluidas (salvo acuerdo adicional)

#### e. Rescisión del contrato
- Incumplimiento del alcance o pruebas no autorizadas
- Riesgo significativo para sistemas de producción
- Violación del NDA
- El cliente retira la autorización
- Falta de cooperación que impida continuar el trabajo
- Acuerdo mutuo entre ambas partes

#### 🎁 Bonus — Cláusulas adicionales recomendadas

| Cláusula | Descripción |
|----------|-------------|
| **Confidencialidad (NDA)** | Toda la información es estrictamente confidencial |
| **Reglas de participación (RoE)** | Define técnicas permitidas, limitaciones y exclusiones |
| **Autorización legal** | Todas las pruebas están autorizadas por el cliente por escrito |
| **Limitación de responsabilidad** | PSS no es responsable por impactos indirectos en sistemas fuera del alcance |
| **Manejo de datos sensibles** | Prohibida la exfiltración de datos reales del cliente |
| **Reporte de vulnerabilidades** | Clasificación: Crítico · Alto · Medio · Bajo |
| **Comunicación de incidentes** | Escalamiento inmediato en caso de hallazgos críticos |

### ✅ Verificación de habilidades
**¿Qué tres secciones se encuentran generalmente en un acuerdo de pruebas de penetración?**
> ✅ **Respuesta correcta:**
> - ✔️ La línea de tiempo del proyecto
> - ✔️ Costos y detalles de pago
> - ✔️ El alcance del trabajo

> ❌ No son parte del acuerdo inicial: nombres del personal de prueba · lista de vulnerabilidades (aún no se han realizado)
